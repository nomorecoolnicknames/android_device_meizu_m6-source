# WHAT THE BLOBS ARE (FACT): stock Flyme for meizu_M6, Android 7.0 / API 24 -
#   /srv/forge/android/meizu_m6/stock-flyme-7.1.2.0G/META-INF/build.prop gives
#   ro.build.version.sdk=24, ro.build.version.release=7.0, ro.build.id=NRD90M,
#   ro.build.fingerprint=Meizu/meizu_M6/meizu_M6:7.0/NRD90M/1553585720:user/release-keys.
#   Every blob here is therefore a Nougat-era MTK binary. That is the root reason
#   this tree is non-Treble and carries no BOARD_VNDK_VERSION.
#
# THE BLOBS THEMSELVES ARE ON THIS DISK (unlike l681's): 492 MB at
#   gunwest-import/m6rom16/rom-work/vendor/meizu/meizu_m6/proprietary/, with a
#   generated makefile tree (meizu_m6-vendor.mk, meizu_m6-vendor-blobs.mk,
#   Android.mk, BoardConfigVendor.mk) next to it. They are NOT copied into
#   los20/vendor/meizu/meizu_m6, deliberately - see the closing block of
#   device.mk for why.
#
# NOT YET DONE (honest status):
#   - this list has NOT been audited against Android 13;
#   - the LOS 16.0 build needs a 40-entry TARGET_LD_SHIM_LIBS cascade to make
#     these blobs link at all (BoardConfig.mk of that tree). Every one of those
#     shims is a statement that a Nougat blob expects a symbol Pie removed; A13
#     removed more. The shim cascade is NOT carried into this tree, because
#     shimming against symbols nobody has checked on A13 would be guessing;
#   - camera: the M6 camera provider still dies at open on the live LOS16 build
#     (H-CAM-2, factbase §5.2) - the fix is built but never flashed. Camera blobs
#     stay in the list, but nothing in this tree declares a camera feature.

# Meizu M6 / MT6750 stock proprietary list
# Adapted from the M5c MTK bring-up pattern, but filtered for this tree.
# Keep the full stock /system/vendor payload; do not copy the whole stock /system.
# ROM-built/core replacements stay out of the active list: libion.so, libtinycompress.so, libgui.so, default power/sensors/memtrack HALs.
# Stock com.meizu.camera.xml stays excluded: it references Flyme framework pieces not present in LOS/CM.
#
# BLOB AUDIT 2026-09-16 (fleet hygiene pass): 4 LINES REMOVED BELOW.
#
#   vendor/lib/mediadrm/libdrmclearkeyplugin.so
#   vendor/lib/mediadrm/libmockdrmcryptoplugin.so
#   vendor/lib64/mediadrm/libdrmclearkeyplugin.so
#   vendor/lib64/mediadrm/libmockdrmcryptoplugin.so
#
# WHY.  Android 13 builds both plugins itself, from frameworks/av/drm, and
# installs them to vendor/lib{,64}/mediadrm/ — the very same destination these
# lines name.  FACT, read off the install rules Soong wrote for a real product
# of this workspace (/srv/forge/android/los20-out/out-m95/soong/
# installs-lineage_m95.mk, `m nothing` for lineage_m95, rc=0):
#   vendor/lib64/mediadrm/libdrmclearkeyplugin.so  <- .intermediates/frameworks/av/drm/...
#   vendor/lib64/mediadrm/libmockdrmcryptoplugin.so <- .intermediates/frameworks/av/drm/...
# A PRODUCT_COPY_FILES rule for the same path silently wins over the built
# module (copy rule from build/make/core/Makefile:72 beats the module rule in
# base_rules.mk:533 / installs-<product>.mk) — the same mechanism that put a
# blob over a source-built hwcomposer on the m5c.
#
# FACT that these blobs really are AOSP code and not a MediaTek plugin of the
# same name — read with `strings` from
#   /srv/forge/android/gunwest-import/m6rom16/rom-work/vendor/meizu/meizu_m6/proprietary/
#   libdrmclearkeyplugin.so   : "ClearKey CDM", "ClearKeyCryptoPlugin",
#                               _ZN11clearkeydrm10DrmFactory15createDrmPluginE...
#   libmockdrmcryptoplugin.so : "mock-defaultUrl", "mock-keyRequestType",
#                               "mock-secure-stop*" (the AOSP mock plugin's
#                               parameter names)
# both built by "GCC: (GNU) 4.9 20150123 (prerelease)", i.e. a 2015 toolchain.
# The 32-bit mock plugin is byte-identical across this dump, the meizu_m6 dump
# and the m681 Flyme 6.2.0.2A dump (md5 679f4ea821ca33531585fba8249121b5), and
# the 32-bit clearkey plugin is byte-identical between this dump and meizu_m6's
# (md5 bf126c16f11587d41c3c8c779524825c) — one AOSP reference build shipped
# across the whole Meizu MTK line.
#
# vendor/lib{,64}/mediadrm/libwvdrmengine.so is NOT in this group and stays:
# Android 13 builds no Widevine, so nothing overrides it.
#
# CHECKED AND KEPT (evidence, not assumption):
#   lib64/hw/fingerprint.default.so — the real sensor HAL: "Goodix Fingerprint
#     HAL", DT_NEEDED libgf_hal.so/libgf_ca.so, gf_hal_* entry points.  AOSP's
#     own fingerprint.default is the "Demo Fingerprint HAL"
#     (hardware/libhardware/modules/fingerprint/fingerprint.c:120).  A13 does
#     build its demo HAL into vendor/lib{,64}/hw/, one directory earlier in the
#     hw_get_module search order (hardware/libhardware/hardware.c:39-45,
#     178-190) than this blob's system/lib64/hw — a reason to install this one
#     under /vendor when the vendor tree is generated, not to drop it.
#   lib64/hw/swfingerprint.default.so — "Sunwave Fingerprint HAL", vendor code;
#     A13 builds nothing by that name.
#   lib/libcurl.so:vendor/lib/libcurl.so — A13 builds external/curl, but only
#     into the VNDK apex (apex/com.android.vndk.v33/lib*/libcurl.so); it never
#     installs a vendor/lib/libcurl.so, and this tree leaves BOARD_VNDK_VERSION
#     unset, so there is no collision and no VNDK rule to break.
#   vendor/lib64/fp_a7/libkeymaster_messages.so,
#   vendor/lib64/fp_a7/libsoftkeymasterdevice.so — AOSP system/keymaster code,
#     but installed into a private directory (fp_a7) that A13 never writes to
#     and no linker namespace searches by default; the fingerprint TEE daemon
#     loads them by explicit path.  Nothing is overridden, so nothing was
#     touched.  HYPOTHESIS: they are dead on A13 together with the rest of the
#     keymaster0/1 path; disconfirm by finding the process that dlopen()s them.
#   vendor/lib{,64}/libperfservicenative.so, vendor/lib/libbt-vendor.so —
#     REJECTED as audit hits.  They do appear in installs-lineage_m95.mk, but
#     the module behind them is device/meizu/m95/shims (stem:
#     "libperfservicenative", libm95shim_btvendor): m95's own shim tree leaking
#     through the root Soong namespace, not AOSP source.  That leak is closed
#     by the soong_namespace {} added to every Meizu device/vendor tree on
#     2026-09-16 (see Android.bp in this directory).
#

# other workspace (see the provenance header above) was NOT edited: it is
# outside this tree.
